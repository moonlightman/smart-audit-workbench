# 智慧审计平台技术方案

版本 V3.0　日期 2026年10月31日

本方案面向集团工程审计业务，建设由六个子平台组成的统一工作台：项目报送平台、数据汇集平台、大数据分析平台、审计管理平台、数据支撑平台、集团信息平台。各平台保留独立入口和业务职责，共用组织账号、项目标识、文件服务和权限体系。前端采用面向PC浏览器的H5应用，首版按集团内部多组织及受邀项目单位协作设计。

建设采用成熟开源组件承担通用能力，定制工程审计的数据模型、业务规则、证据定位和成果流程。先完成六个平台之间的数据闭环，再逐步扩大分析模型和系统对接范围。本版形成架构与实现决策，明确技术验证、开发工作包和验收方法，作为后续详细设计依据。开源版本组合经实际验证后冻结。

## 一 建设定位与功能范围


### 1.1 核心目标与设计约束

本项目建设统一智慧审计工作台，保留六个平台的完整业务职责；集团信息平台由人工维护合同、制度、各地造价信息和汇编，提供查阅下载；优先复用已有开源项目；前端为仅面向PC的H5应用；平台运行时涉及大语言模型的功能统一调用DeepSeek。

子平台既有独立业务入口，也共享数据与流程。采用一个后端部署单元并不取消子平台边界；分期启用组件也不删除SQL分析、智能问答、量价分析及数据汇集等总体功能。本文所列外部接口、厂商格式与湖仓能力均保留建设项，逐项明确依赖和交付门槛。

### 1.2 建设目标

将建设单位报送、资料整理、数据分析、审计实施、知识查询和集团资料共享放在同一工作环境中。用户从工作台进入相应子平台，在授权范围内查看同一项目的资料、问题和办理进度。

主要形成三条可持续运行的业务链：工程资料从报送到核验归档；分析问题从发现到复核处理；集团资料从人工发布到查阅下载，并在审核后进入数据支撑体系。

### 1.3 六个平台的职责分工

本项目按资料报送、数据治理、分析计算、审计实施、知识支撑和集团共享划分六个平台。各平台有独立入口、权限和工作流程，通过项目、合同及文件版本关联。备案审核与地图监管预留扩展入口，按实际需要另行建设。

| 本项目平台 | 对应职责 | 本项目落地重点 |
| --- | --- | --- |
| 项目报送平台 | 工程全过程信息报送 | 项目台账、分阶段表单、资料目录、补正与版本 |
| 数据汇集平台 | 多源接入、整理和汇聚 | 接口同步、文件解析、标准化、质量校核、来源追溯 |
| 大数据分析平台 | 文档识别、查询分析、量价比对 | 审计模型、差异明细、风险线索、结果复核 |
| 审计管理平台 | 审计任务与质量控制 | 人员计划、底稿、对账、三级校审、报告、整改 |
| 数据支撑平台 | 造价、指标、法规与成果知识 | 结构化参考库、检索、带出处的智能问答 |
| 集团信息平台 | 人工资料共享与发布 | 人工维护合同、制度、造价信息、汇编，提供查阅下载 |

表单、规则、技术组件和实施路径由本项目需求决定，实施时以功能清单、数据字典、样本和验收条件固定交付范围。

## 二 总体架构

### 2.1 统一工作台与六个平台

工作台提供六个平台入口、我的待办、项目检索、近期资料、分析任务状态及项目总览。进入任一项目后，平台之间保持项目上下文，能够从分析问题跳转到原文件，从审计任务进入对应底稿，从制度引用定位到指定版本。

平台在产品和代码层面划分业务边界。首版核心业务采用模块化后端，OCR、文档转换、分析计算、数据同步作为独立任务服务部署；后续按负载和团队分工拆分服务。这样可以先统一账号和数据口径，同时保留子平台独立扩展的空间。

```text
PC浏览器 H5统一工作台
  ├ 项目报送平台       ├ 数据汇集平台       ├ 大数据分析平台
  ├ 审计管理平台       ├ 数据支撑平台       └ 集团信息平台
                         ↓ 统一API与身份校验
业务模块：报送  数据治理  分析任务  审计流程  参考数据  资料发布
                         ↓
共享服务：组织权限  项目目录  文件版本  流程待办  消息  操作记录
                         ↓
任务服务：解析与OCR  规则与AI分析  ETL同步  文件预览转换
                         ↓
数据底座：业务数据库  原始文件存储  分析数据集  全文索引及预留向量能力
                         ↓ 按规模演进
湖仓扩展：Iceberg表格式  元数据目录  Trino查询  统一权限与血缘
```

PostgreSQL作为首选验证数据库。已核验RuoYi-Vue-Plus v6.0.0的依赖声明：Java 21、Spring Boot 4.1.0、WarmFlow 1.8.9，且该标签提供PostgreSQL初始化及工作流脚本。[S16] 这些属于源码依据，不能替代启动、迁移、流程和恢复实测。若该组合验证失败且修复成本明显高于备选，再验证MySQL，最终只维护一种生产数据库。前后端、JDK、框架、流程、数据库、缓存与存储客户端以完整兼容矩阵冻结。

### 2.3 子平台集成约定

六个平台使用同一套项目ID、组织ID、人员ID、文件ID和权限规则。业务数据由所属模块维护，其他模块通过接口、事件或受控分析视图引用。分析平台不直接修改合同台账，集团信息平台不直接修改审计底稿。

系统内部通过REST API交换业务数据。文件解析、同步和分析通过持久任务接口异步执行，返回任务ID，由前端展示排队、运行、成功、部分失败和失败状态。核心业务事务内写入任务或事件记录，后台投递；任务按业务键与版本防止重复执行，并支持重试和人工补偿。


### 2.4 组件启用与工程组织

首版采用一个Vue工作台、一个Java核心业务应用和独立Python worker。人工业务由WarmFlow编排，机器作业由任务系统执行。核心业务模块通过服务接口调用，数据库迁移按模块管理；共享主数据由所属模块维护，其他模块使用服务或只读模型。

| 启用节点 | 运行组件 | 交付目的 |
| --- | --- | --- |
| 基础试点 | Vue工作台、Java业务、PostgreSQL、兼容缓存、S3存储、Python worker | 报送、集团资料、文件、流程与样本任务 |
| 检索交付 | OpenSearch、中文分析器、索引任务 | 集团全文检索与支撑库检索，完整交付前启用 |
| 解析交付 | Tika、PaddleOCR、隔离文档转换程序 | 按文件类型启用插件或独立容器 |
| 专业分析 | 隔离分析数据空间，按需Superset | SQL、图形查询和嵌入看板 |
| 外部接入 | 按需SeaTunnel | 已确定来源系统的同步任务 |
| 规模扩展 | Iceberg、目录服务、Trino | 明确规模与查询场景的湖仓专项 |

不直接启用底座演示配置中的全部扩展服务。每个启用组件都须有部署版本、资源限额、负责人、监控、备份或重建方式及升级回退办法。兼容缓存优先验证Valkey，若客户端锁语义或协议不兼容，再选经核查的兼容开源缓存版本；不在未验证时替换生产锁组件。

代码按portal、submission、ingestion、analysis、audit、reference、group-info及shared拆分。Python侧按文档解析、OCR、清单分析和知识索引拆分任务处理器。API契约和任务载荷采用版本化JSON Schema；数据库变更采用可回放迁移脚本，前端依赖与后端依赖锁定。


## 三 工程实现中的关键协议

### 3.1 项目授权与分析域

服务端统一计算“用户＋组织＋项目成员＋操作＋资料状态”的授权结果。项目ID、文件ID和授权域均由服务端验证，不能相信浏览器传入的范围。集团管理人员、审计团队、受邀建设单位和资料维护人员使用不同能力授权；受邀单位默认只见受邀项目。

查阅、下载、填报、分析、复核、发布分别授权。授权域是明确审批的组织与项目集合、数据分类及脱敏范围，具有负责人、成员、版本和有效期。权限变化递增授权版本，使查询、导出、任务和问答缓存失效；停用后阻止新的访问。对过去已经显示或下载的内容不能技术性收回。

所有API、搜索片段、数量聚合、预览、证据链接、批量导出及后台结果均覆盖相同授权规则。原件、预览及成果统一经应用代理访问，每次新请求及分段读取均校验权威状态。面向用户的接口不返回可绕过应用鉴权的存储签名链接，以满足撤权后的访问约定。已经传输给用户的字节无法收回。

### 3.2 SQL查询的数据库边界

普通用户使用授权字段和指标构建受控查询，参数化执行。SQL专家按审批进入分析域，每个域绑定受限数据库角色和受控视图或隔离数据空间；原始业务表、跨域空间、管理员角色与无关系统函数不向查询账号授权。成员以自己的平台身份访问，后端记录用户与域，数据库凭据只由服务端保管。

同一宽范围只读账号配合前端筛选不能实现个人项目隔离。域内专家具备域内全量访问权，因此人员范围必须一致；跨域人员选择单个域执行，跨域联合查询使用另行审批的数据集。撤权时停止新查询，取消进行中的查询，作废可下载结果并回收域访问；域变更需同步视图、凭据与缓存版本。

Superset仅连接这些已隔离数据源。图表、SQL Lab、缓存、嵌入和导出分别验证；不能用看板RLS推定任意SQL受到相同保护。[S17] 使用PostgreSQL行级策略时必须验证数据库角色、表所有者及绕过权限，任意SQL用户不能自行设置一个被当作可信身份的会话变量。[S18]

### 3.3 不可变文件与证据定位

文件业务记录、字节对象、文件版本、发布版本、解析版本和分析快照分别建模。相同字节可复用存储，但不同业务记录独立授权，不能因哈希相同继承其他项目权限。对象键使用不可变版本，原件更新新增对象，禁止覆盖旧版本。

上传先写临时对象，校验大小、类型、完整性和哈希后，由业务事务确认文件版本；失败记录补偿任务，定期清理无引用临时对象。数据库和对象存储不属于同一事务，不能假定二者总是同时成功。

PDF证据保存原文件版本、原页码、页面尺寸、旋转角、坐标系及文本片段；预览另存转换版本和坐标变换。Excel证据保存工作表标识、单元格或区域、原公式与缓存值。DOCX证据保存段落或表格锚点及指定预览版本。无法精确高亮时明确退回页级或原件定位，不显示伪精确坐标。

### 3.4 业务状态机与工作流

报送、发布、底稿和整改各自定义合法状态、可操作角色、业务版本和前置条件。业务表为状态权威，WarmFlow负责人员与步骤编排。典型底稿状态为草稿、待复核、待审定、已审定；退回、撤回、终止由明确迁移处理。

流程实例与提交时的业务版本绑定，回调以流程实例ID和事件ID去重，并校验事件顺序、当前状态与乐观锁版本。两个审批人并发提交只允许一个有效迁移。岗位调整和委托有授权记录，职责冲突需阻止。已审定版本修改生成新版本，重新校审。

若引擎与业务共享数据库事务，应实际验证事务边界；若跨进程，先进入“启动中”等中间态，业务事务写出站事件，再异步发起流程。流程发起及回调均幂等，定期对账实例状态与业务状态，失败进入可处理补偿队列。

### 3.5 持久任务与过期执行隔离

试点默认采用数据库任务表＋事务outbox＋独立worker，复用数据库事务和锁能力，只实现项目需要的任务协议。业务变更与outbox同事务提交，后台投递至少一次，消费方幂等。数据库任务记录为业务状态权威，消息或轮询负责唤醒执行。

任务保存job_id、项目、任务类型、输入快照、规则与模型版本、去重键、状态、尝试次数、下次执行时间、租约到期、递增令牌、输出清单和错误码。状态至少包括排队、执行、等待重试、成功、部分成功、失败待处理和取消。

worker经内网任务API原子领取并取得租约及递增令牌，定时心跳续租；重新领取产生更大的令牌。心跳、阶段结果和最终提交必须校验当前令牌、状态和租约。旧worker超时后即使恢复，也不能覆盖新执行结果。worker不直接修改审计业务表，只能读取分配任务的文件和写入指定临时输出区。

每次尝试使用独立临时输出，服务端确认哈希、输入快照、业务版本及有效租约，并重新校验发起人的当前授权版本、输入资料及参考条目是否仍允许用于本次任务后，原子登记唯一有效结果和输出引用。授权失效则拒绝发布，输入撤回则进入待复核或取消，不静默形成可用结论。重复提交返回已有结果，失败遗留对象由补偿任务清理。取消需先提交取消状态，使后续提交被拒，再尽力停止计算，不能仅杀进程。

OCR按页或文件分片建立检查点，解析与AI调用分别限流、限时、限次数。网络错误有限退避重试，格式错误、资料不足及权限失效进入待处理或取消。模型费用、通知和外部写入分别定义幂等与补偿，外部服务不提供幂等保障时不能承诺只调用或计费一次。

阶段0用同一批任务比较自建协议与成熟队列的开发维护代价。若需要复杂链式编排、大量定时延迟任务，或任务协议故障验证不能通过且修复成本更高，则切换Celery＋RabbitMQ。切换仍保留业务任务表、outbox和结果幂等；成熟队列并不自动提供业务上恰好一次的执行效果。[S19]

### 3.6 发布撤回与派生数据

资料发布、撤回或权限变化时，业务事务同步更新状态、资料事件序号及outbox。索引事件携带资料ID、版本和单调递增序号，消费者只接受比当前更新的事件；旧发布事件不能覆盖新撤回状态。后台周期核对业务状态和索引版本，支持重建。

检索查询先限定授权范围，召回后检查权威状态；送入模型前再查，输出答案前再次核验引用资料及用户授权版本。生成中发生撤回或撤权，阻止新答案输出并返回资料状态变化提示。输出校验以权威读取时点为准，已经传给外部模型或已显示的内容不能追溯收回，因此严格时效场景采用整段生成后校验再展示。

撤回同步影响全文、向量、摘要、问答缓存、价格条目和进行中的新分析。参考价格条目在权威库标记停用，分析读取与提交时均检查其状态，不依赖索引是否已更新，不再进入新基准；既有审计快照作为历史记录保留，标明来源已撤回并按历史档案权限访问。修正不静默重写审定结论，重新计算建立新版本并走复核。

### 3.7 工程数据与AI的计算边界

电子表格优先读取原始单元格、公式与缓存。缓存缺失时标为待复算；若确需重算，在隔离环境执行且不启用宏或外部链接，保留引擎版本。OCR金额、单位、税率及跨页表格均进入质量核验。

清单匹配先按工程层级、编码、单位及施工范围筛选，再结合规格、品牌、工艺和环境生成候选。每家单位独立保存原始特征、差异、可比结论及理由。映射未确认、不可比、重复或算术异常不进入同行基准，缺报价不按零，历史库为空仍可做原始报价分析。

规则与模型输出保存输入快照、参数、模型与提示词版本、运行标识、证据及复核记录。金额和量价分解由十进制定点程序完成；模型解释与确定性计算分开保存。专有造价格式按厂商、版本、导出路径及字段覆盖登记，不以能打开文件替代完整量价验收。


### 3.8 DeepSeek统一接入

平台业务中的条款理解、候选清单匹配、差异解释、摘要、知识问答、报告建议和自然语言查询解释全部调用DeepSeek。OCR、全文检索、统计、字符串相似性和金额计算仍使用相应开源算法；它们不调用其他LLM。Codex与Dot属于开发协作工具，不作为审计平台对终端用户提供推理的后端。

采用内部DeepSeek调用服务，浏览器、业务模块和解析任务均不能各自配置模型厂商。固定provider为deepseek，出口限定DeepSeek官方域名；密钥在服务端注入，开发、测试和生产分别管理。不得把平台API密钥写入前端、代码仓库或任务提示词。

| 配置项 | 本版约定 | 管理方式 |
| --- | --- | --- |
| 提供方 | DeepSeek | 服务端固定，不提供其他LLM兜底 |
| API入口 | https://api.deepseek.com | 官方入口白名单，按所选协议调用 |
| 常规模型 | deepseek-flash | 当前候选，结构提取及问答样本通过后冻结 |

| 输出规范 | JSON Schema与业务校验 | 服务端校验必填、类型、证据与业务约束 |
| 调用控制 | 超时、并发、重试、费用及次数上限 | 按任务、项目、组织分别统计 |

模型名称与能力依据核查日的DeepSeek官方文档，部署时重新核对可用性并冻结配置。[S21] 保存请求模型名、响应模型名、官方版本映射记录、提示词版本及输入输出哈希；服务端模型别名更新不等于完全可复现原推理。接口费用与Codex或Dot的订阅费用分别预算。

先使用稳定的文本对话接口完成业务集成。结构化任务启用JSON Output并提供输出示例，返回后仍执行本地Schema及业务校验；有效JSON不能证明金额、依据和结论正确。对空白返回、截断、字段缺失和无法识别的响应进入有限重试或人工核验，不编造缺失值。[S22]

工具调用只开放已经实现并授权的只读查询与计算工具，由服务端校验参数并执行。模型提出工具调用不等于实际执行；不得允许模型直接执行任意SQL、操作文件系统或审批发布。Beta严格模式仅在接口兼容验证后使用，不作为首版交付前提。[S23]

可重试错误采用退避和预算约束；鉴权失败、输入超限、资料撤回或费用达到上限不盲目重试。DeepSeek不可用时暂停相关LLM任务，仍可继续文件查阅、人工录入和确定性核算，显示真实状态，不切换其他LLM。模型回复经权限复核后再展示，不默认记录隐藏推理内容。

知识检索先检查资料范围与有效版本，再发送最少必要片段给DeepSeek，回答必须携带来源ID。自然语言生成的查询仅作为受控候选，继续执行数据库权限和SQL校核。政策判断和审计结论均需业务人员复核。

## 四 项目报送平台

### 4.1 功能范围

以工程项目为报送单元，建立“项目—标段—合同—业务事项—附件”的关联。报送平台负责收集、补正和确认资料，形成后续审计可使用的数据来源。

| 报送分类 | 主要内容 |
| --- | --- |
| 资金筹集 | 资金来源、概算批准金额、预算下达、资金到位及拨付记录 |
| 项目前期 | 项目立项、可研、勘察、用地与规划许可、施工许可等资料 |
| 招投标 | 招标文件、控制价、投标文件、开评标记录、中标结果 |
| 合同 | 合同类型、双方、金额、日期、付款条件及补充协议 |
| 征地拆迁 | 批复、补偿协议、对象、金额、支付及安置情况 |
| 施工过程 | 开工、进度、预付款、计量、进度款、变更签证和其他建设费用 |
| 竣工阶段 | 验收、送审结算、审定结算、竣工决算与相关报表 |

### 4.2 报送流程

项目管理员配置报送目录和责任单位。填报人填写结构化表单并上传附件，系统检查必填字段、金额日期格式和目录完整性，再提交资料审核人员。审核通过后形成报送批次快照；退回时记录补正要求，重新提交保留前后版本。

目录完整性只表明要求的资料是否已提交，内容真实性、价格合理性和业务合规性由后续审计环节核实。每份文件记录归属项目、合同、资料分类、提供单位、版本、上传人、上传时间和内容哈希。

### 4.3 开源复用与开发内容

复用底座的表单管理、权限、上传和流程能力；定制七类工程报送表单、附件目录、批次快照、补正清单和跨表校验。首版支持网页填报、Excel模板导入、批量附件上传；按外部系统条件增加接口报送。

## 五 数据汇集平台

### 5.1 数据接入与整理

统一接收报送平台资料、集团信息平台已发布资料、经授权的外部业务数据及历史审计成果。数据接入采用文件导入、标准API和数据库同步三种方式，保留来源系统、采集时间、同步批次和原始主键。

对于财务付款、合同管理、招采及人员数据，按具体来源系统确认接口字段、更新频率和访问权限。涉及公开信息采集时，按来源条件设置采集任务；人工维护的集团资料不因技术接入而自动改写发布内容。

### 5.2 数据处理流水线

原件落库后先识别文件类型，再按格式解析。电子Excel按单元格和公式读取，DOCX提取段落及表格，具有文本层的PDF优先提取文本；扫描件使用OCR。提取结果同时保留原文位置、解析版本和质量状态。

标准化处理包括组织与项目名称映射、日期格式、币种、金额单位、计量单位、税率和清单编码。保留原值、标准值、转换规则和处理人。缺失金额、未报价、无法识别分别标记，不自动补零；疑似重复先建立关联，由规则或人员确认。

数据质量问题进入待处理队列，例如合同金额与附件不一致、累计付款口径冲突、清单单位缺失、来源文件损坏。未经确认的结果可供核验查看，但不进入要求有效数据的分析基准。

### 5.3 数据分层

| 数据层 | 存放内容 | 使用规则 |
| --- | --- | --- |
| 原始层 | 原文件、源系统记录、采集批次 | 保留历史，便于重放和核对 |
| 整理层 | 提取字段、标准化值、质量标记、业务关联 | 支持校核与修正 |
| 分析层 | 经确认的数据集、指标、版本快照 | 提供分析与报表的稳定输入 |

首版以对象存储、数据库分层表和分析快照实现上述业务能力。规模扩大后，采用对象存储、Iceberg、元数据目录与Trino构建湖仓能力，补齐表快照、统一查询、权限及数据血缘。[S13][S14] 轻量首版作为演进起点，不将“保存了文件和业务表”等同于已经建成湖仓一体平台。

### 5.4 开源复用与开发内容

SeaTunnel用于数据同步，[S4] Tika用于文件类型识别和通用文本提取，[S5] PaddleOCR用于扫描件识别。[S6] 自研工程字段映射、清单匹配、质量规则、来源定位及纠错界面。同步工具的连接器不能直接替代工程资料解析和业务可比性判断。

## 六 大数据分析平台

### 6.1 文档识别与文本分析

提供招标文件条款提取、合同关键字段提取、投标技术文件相似片段比对及委托人员信息提取。招标评分条件由规则和AI识别潜在限制性条款，显示原文与适用依据，交由人员复核。

技术文件相似性分析需要排除统一模板、规范引用及项目通用要求，呈现相似段落与来源页码。报价规律、文本相似和统计模型输出均作为审查线索，不自动认定违法违规或围串标。

委托人员与社保缴纳单位的核验，依赖合法授权的外部接口或用户提供的证明材料。未接通数据源时显示“未核验”，OCR只承担信息提取。

### 6.2 人工查询与SQL分析

普通审计人员通过筛选字段、选择指标和关联条件进行查询；具备权限的分析人员通过SQL工作区查询只读分析数据集，查看查询计划与运行状态。可复用Superset的数据探索能力，并对接统一身份与数据权限。[S7]

SQL查询使用受限数据库账号和授权视图，控制运行时长、返回行数、并发和导出量。浏览器端隐藏菜单不能替代查询权限；自然语言生成SQL也需经过同样的只读与数据范围控制。

### 6.3 量价分析

建立统一造价明细模型，覆盖单项与单位工程、分部分项、措施项目、其他项目、人材机、管理费利润及税费。支持控制价、中标价、送审价、审定价之间的版本对照，并展示新增、删除、数量变化、单价变化、取费变化及金额影响。

优先通过Excel和公开交换格式建立标准清单；专有造价文件采用厂商导出、授权SDK或单独格式适配。网页中的量价分析功能属于本项目建设目标，但完整商业计价软件、图纸自动算量及全国定额解释引擎需要专项集成与验证。

| 分析方向 | 处理方法 | 结果输出 |
| --- | --- | --- |
| 算术核查 | 检查量乘价、明细与汇总、税费计算及舍入差异 | 差异位置、原值、复算值 |
| 多家报价比较 | 确认项目特征、单位、范围及映射后比较 | 对比明细、偏差、澄清事项 |
| 版本量价对照 | 对照工程量、单价、费率及项目增减 | 差异原因、金额影响及证据 |
| 不平衡报价 | 联合金额贡献、工程量变化和支付时序筛查 | 风险线索和人工复核意见 |
| 规律性分析 | 观察报价比例、共同错误及其他关联证据 | 可核对的异常点和排查记录 |
| 支付与变更核对 | 联合合同条件、计量、付款及签证资料 | 超付、重复或资料缺失线索 |

金额使用十进制定点计算，记录币种、含税状态、精度与舍入规则。对于数量与价格变化，可按“数量影响＝新旧数量差×旧单价；价格影响＝新数量×新旧单价差”分解，二者合计应等于合价差。新增、删除及不可比项目单列，避免强制配对。

### 6.4 分析任务与证据链

每次分析保存任务ID、输入快照、参数、规则版本、模型标识、执行时间和结果状态。每个问题保存关联项目、合同、明细行、文件版本、页码或单元格、计算过程和复核意见。数据修正后新建分析版本，保留旧结果。

AI承担文本理解、候选匹配、差异解释和问题建议；程序承担金额计算、规则执行及稳定成果生成；业务人员确认资料适用性、可比性和最终结论。已有回标分析能力应先核验代码、输入输出协议和运行依赖，再封装成独立任务服务接入。

## 七 审计管理平台

### 7.1 审计业务范围

覆盖预算审计、控制价审计、结算审计、决算审计和跟踪审计。按审计类型配置任务模板、资料清单、底稿目录和审批路径，形成项目初始化、计划实施、现场记录、对账、校审、报告及归档的全过程记录。

预算、控制价、结算和决算审计包含人员分配、实施方案、现场踏勘、对账、三级校审、重大争议、进展上报、会议纪要、项目考核及报告版本。跟踪审计增加进退场证明、预付款和进度款审查、计量与签证、其他建设费用、考勤与审计日志、月报及总结。

### 7.2 问题与底稿办理流程

分析任务可生成待复核问题，经审计人员确认后关联底稿，向责任方发出补充资料或反馈要求。收到解释与证据后，记录采纳、部分采纳或不采纳及理由，再进入校审。整改事项关联责任单位、期限、反馈资料和验收记录。

三级校审配置编制、自校、复核、审定等实际岗位关系，按集团制度确定三个校审层级与签署要求；同一人员不得以不同角色完成存在职责冲突的校审环节。退回后保留修改记录，已经审定的底稿以新版本重新发起流程。

### 7.3 成果与扩展

结构化底稿、问题清单和审计记录统一保存。首批自动生成成果优先落地固定Excel；正式审计报告支持上传、修订、审批及归档，自动排版按后续确认的模板建设。生成文件必须绑定数据快照和模板版本。

按后续业务需要，可在审计管理平台内扩展备案发起、补充填报、抽查复核、备案审核及通知书。工作台可增加地图总览；现场视频依赖现有视频系统授权对接。上述内容单独估算，不改变六个平台的总体划分。

## 八 数据支撑平台

### 8.1 参考数据与知识体系

建设清单库、定额库、材料价格库、人工指导价库、造价指标库、政策法规库、公共专业知识库及审计成果库。各库记录数据来源、地区、专业、适用时间、版本和审核状态。

材料与人工价格保留规格、品牌、单位、税费、价格类型、时间和地区，区分指导价、询价与项目成交数据。造价指标按工程类型、规模、建设标准和计价时点分组，展示样本范围。缺少可比样本时说明不足，不把同行中位数写成合理市场成本。

### 8.2 智能问答

采用“权限过滤—检索—必要的排序—生成答案—出处展示”的流程。答案引用具体资料版本与段落，并展示发布单位、适用地区和时间。法规适用与项目结论需要审计人员确认；找不到依据时返回资料不足，不生成无来源的判断。

首版通过OpenSearch中文全文、结构化字段和BM25检索提供知识召回，再由DeepSeek依据授权片段回答。后续向量能力单独验证，首版不依赖未核实的向量接口，也不因此接入其他厂商LLM。可基于OpenSearch和LangChain组织仅调用DeepSeek的检索流程，所有LLM请求经统一后端服务调用DeepSeek官方API，允许在经过验证的DeepSeek模型之间切换，不接入其他厂商LLM或本地替代LLM。[S9][S12] 文档正文作为待分析内容处理，不赋予其修改系统权限、执行代码或指挥流程的能力。

### 8.3 与集团信息平台的边界

集团信息平台维护供人阅读和下载的原始资料及发布状态；数据支撑平台维护供检索、比价和分析调用的条目、指标和知识索引。二者共用文件ID和版本ID，分别管理发布与数据质量。

例如，资料管理员上传某市某月造价信息汇编，经审核发布后可供授权用户下载。数据支撑平台另行建立提取任务，校核材料名称、规格、单位、价格口径、地区和月份，审核通过的条目才能参与分析。能下载该汇编不代表其内容已经全部变成可计算的价格数据。

## 九 集团信息平台

### 9.1 平台定位与栏目

作为集团统一资料中心，由人工收集、分类、维护、审核和发布，提供PC网页查阅与下载。主要栏目包括合同范本与经授权的合同资料、集团制度及流程、各地造价信息、专业汇编。可根据维护需要增加政策文件、业务指南和案例资料。

合同范本与已签项目合同分别设置分类和权限。涉及具体项目的合同仍以项目台账为业务主记录，集团平台通过关联引用或经审批的共享版本展示，保留原有密级与访问限制。

### 9.2 资料维护与发布

维护人员创建资料记录，填写标题、分类、来源、地区、专业、发布日期、适用时间及标签，并上传原件。审核人员确认内容、共享范围、可下载范围和有效状态后发布。更新资料生成新版本，记录替代关系；撤回、失效和到期提醒均留存处理记录。

建议流程为“草稿—待审核—已发布—已失效或已撤回”。草稿和退回资料仅维护人员可见，普通读者默认访问当前有效版本；允许查看历史版本的岗位可按权限追溯。

### 9.3 查询与阅读体验

支持按标题、正文、地区、月份、专业、资料类型和状态检索；支持分类目录、最近更新、收藏和相关资料。资料详情展示版本、生效时间、来源、维护部门及附件，提供预览和下载。

PDF使用PDF.js预览，[S10] Office文档通过后台隔离转换生成预览PDF，原件保持可下载。转换失败时明确提示并按权限提供原件。首版实现查阅下载即可，在线编辑和多人协作文档按后续实际需求增加。

### 9.4 数据字段与权限

| 字段组 | 建议字段 |
| --- | --- |
| 基础信息 | 资料ID、标题、栏目、标签、摘要、维护部门 |
| 适用范围 | 地区、专业、年份月份、适用组织、资料类型 |
| 版本时效 | 版本号、发布日期、生效日期、失效日期、替代资料ID |
| 来源文件 | 来源单位或网址、文件ID、原件哈希、附件名称 |
| 发布记录 | 状态、维护人、审核人、发布时间、撤回原因 |
| 访问范围 | 可查阅组织、可下载组织、项目范围、保密等级 |

查阅与下载分别授权，后端在每次访问时校验身份、组织、项目及资料状态。预览是受控阅读方式，无法承诺技术上阻止用户截屏或复制已显示内容。文件存储不开放公共目录；原件与预览均经应用代理下载或读取，存储路径不直接交付浏览器。

### 9.5 与数据支撑平台联动

发布或更新后生成索引任务，携带资料ID、版本ID和访问范围。撤回与权限变化首先提交权威状态和授权版本，即时阻断后续访问；旧索引和缓存通过事件异步清理并最终收敛。检索、模型上下文和答案输出前均复核权威状态，不等待索引刷新。问答引用必须能够打开相同版本的来源。

该平台采用统一底座的内容管理模块加文件预览服务实现，复用账号、流程、文件和搜索。人工维护是发布前提，自动OCR和索引仅辅助查找，不自动代替人工确认与发布。

## 十一 数据流与核心对象

### 11.1 两条主数据流

工程审计数据流为“项目报送—原件归档—解析整理—人工或规则校核—分析快照—问题复核—底稿校审—成果归档”。问题处理结果回到审计管理，数据纠错回到数据汇集，经过审核的成果摘要可进入数据支撑库。

集团资料数据流为“人工维护—审核发布—查阅下载”，并在授权范围内分出“提取索引—知识或价格条目审核—检索问答与分析引用”的路径。资料原件、发布版本和结构化条目始终保持关联。

### 11.2 核心数据对象

| 对象 | 关键关联和用途 |
| --- | --- |
| 组织 用户 项目成员 | 控制集团、下属单位及受邀单位的数据范围 |
| 项目 标段 合同 | 统一项目与合同主线，区分合同类型与版本 |
| 文件 文件版本 来源位置 | 保存原件、哈希、页码、段落及单元格定位 |
| 报送批次 数据集版本 | 冻结特定时点的输入与质量状态 |
| 造价明细 付款 变更签证 | 支持工程量、价格、合同和支付关联分析 |
| 分析任务 规则版本 问题 | 保存参数、计算证据、解释与处理状态 |
| 底稿 校审 报告 整改 | 支持审计过程与成果责任追溯 |
| 集团资料 发布版本 参考条目 | 关联人工发布内容与支撑平台引用 |

### 11.3 接口约定

接口按项目、报送、文件、分析、审计、知识及集团资料分组，使用版本化路径，例如“/api/v1/analysis/jobs”。创建长任务返回任务ID；查询任务返回进度与失败明细；下载和证据接口逐次鉴权。

原始文件只新增版本；更正记录操作者、原因和时间。数据库写入与后台任务通过事务事件衔接，失败可重试。索引为可重建的派生数据，业务数据库与文件原件为权威来源。

跨模块写入只调用所属模块的业务接口或事件处理器，不从Python或BI直接修改业务表。事件载荷包括event_id、aggregate_id、aggregate_version、schema_version、项目ID、关联任务ID及时间。HTTP写入支持幂等键，按用户、项目、操作及请求内容绑定；相同键内容不一致返回冲突，不能复用旧结果。



主要接口在详细设计中按以下契约展开；业务接口面向登录用户，内部任务接口只面向经认证的worker。

| 方法与路径示例 | 调用主体 | 关键约定 |
| --- | --- | --- |
| POST /api/v1/submissions | 项目填报人 | 幂等创建，提交时绑定项目与批次版本 |
| GET /api/v1/files/{id}/content | 授权查阅或下载人 | 应用代理、分段读取鉴权、按版本返回 |
| POST /api/v1/analysis/jobs | 授权分析人 | 返回任务ID和输入快照，不阻塞等待 |
| POST /internal/v1/jobs/claim | 机器身份 | 原子领取，返回租约及递增令牌 |
| POST /internal/v1/jobs/{id}/commit | 持有有效租约的worker | 校验令牌与当前授权后幂等提交 |
| POST /api/v1/group-docs/{id}/publish | 发布审核人 | 业务版本校验，事务写状态与出站事件 |
| POST /api/v1/group-docs/{id}/withdraw | 授权维护与审核岗位 | 即时更新权威状态，异步清理派生数据 |

接口统一区分未登录、无权限、版本冲突、输入校核失败及任务失败；文件或项目不存在与无权限时按统一策略避免泄露对象存在性。日志使用trace_id关联业务请求、事件、任务尝试和输出版本，错误提示不回显敏感正文。

## 十二 PC端H5交互设计

### 12.1 页面结构

统一顶部保留集团标识、项目切换、检索、消息和用户入口；左侧显示当前平台菜单；主区域展示台账或具体业务。六个平台采用一致的筛选、表格、状态、详情和导出方式。

审计与分析详情采用“事项目录—结果与处理—原文证据”布局，并允许折叠侧栏。集团信息平台采用“分类目录—资料列表—详情预览”布局，便于查找和下载。

### 12.2 使用标准

以1920×1080为主要设计尺寸，兼顾1366×768；复杂表格支持冻结关键列、横向滚动、分页及大数据量虚拟滚动。浏览器以受支持的Chrome和Edge版本为验收对象，版本范围在实施时冻结。

OCR、批量导出和AI分析在后台执行，页面切换或关闭后任务仍可查询。上传提供进度、失败原因和重试入口。所有关键操作显示明确结果，避免用户因等待重复提交。

首版仅设计PC工作流程和桌面浏览器交互。H5指基于HTML5的浏览器应用，核心业务可统一为单页应用及模块路由，后端任务与文件处理不在浏览器中直接执行。

## 十三 部署运行与实施安排

### 13.1 部署建议

采用可私有化部署方式，按Web入口、核心业务、数据库与文件、解析与计算划分部署单元。开发和试点可使用容器编排配置启动，正式环境按访问量和恢复要求分离核心服务与数据服务。只有出现多节点调度和独立扩容需求后再引入Kubernetes。

试点资源可从应用节点8核16GB、数据与文件节点8核32GB、解析计算节点8核16至32GB起测；全文服务启用后单独评估内存、磁盘和索引增长，不能将其资源默认包含在数据库额度内。这些仅为压测起点。扫描页数、索引体积、并发解析任务和DeepSeek接口并发策略决定最终配置；首版LLM使用DeepSeek API，不配置本地LLM推理GPU；OCR是否需要GPU按扫描样本评估。存储容量按原件、历史版本、预览件、索引和备份共同测算。

部署前验证文件存储、数据库及缓存客户端兼容性。对公网报送入口与内部管理入口配置不同访问策略，数据库、存储与管理控制台仅在受控网络暴露。文件转换在隔离进程或容器中运行，限制文件类型、执行时长及资源。

### 13.2 运维与恢复

统一记录登录、资料发布、原件下载、数据更正、分析和审批操作。保留操作业务标识，避免在普通日志中写入完整身份证、合同正文和访问凭据。对任务失败、解析积压、磁盘容量和索引延迟设置可处理的告警。

定期备份数据库、文件原件及配置，验证恢复后文件与记录能够对应。候选试点恢复目标为RPO不超过24小时、RTO不超过8小时，实际值由备份与恢复演练确认。正式运行前完成数据恢复和版本回退演练。

| 技术验证 | 字段目录、资料样本、底座兼容、OCR及造价格式验证 | 功能清单、数据字典、版本清单、页面草图 |

不再以固定人数和日历周数作为六平台整体交付预期。阶段0明确页面、表单、流程、文件格式、接口及样本后，按“工作包×角色人周＋依赖等待＋风险缓冲”形成WBS，并标注并行任务和关键路径。单独跟踪厂商SDK、财务等接口、制度确认、数据整理、DeepSeek接口开通和验收人员等待。

建议明确工程审计业务负责人、产品与实施、后端与架构、PC前端、解析与AI、测试、运维安全七类责任；可兼任的岗位需评估工作量，审批职责仍按制度分离。每个阶段由技术负责人和业务负责人共同核对交付清单，不通过压缩测试时间换取日历进度。

### 14.2 性能与识别质量验证

建立带人工标注的样本集，覆盖不同专业、清单格式、扫描质量和表格复杂度，分别衡量关键字段正确率、金额正确率、问题误报漏报和原文定位。识别服务不能仅用普通文字准确率证明工程金额可直接用于审计。

候选试点性能场景为50名在线用户、10名用户同时进行常规查询及3个后台解析任务；普通列表与资料检索P95目标不超过3秒。测试记录数据库规模、文件体积、硬件及缓存条件，OCR与AI任务按页数和文件类型单列耗时。上述为设计目标，须由试点压测形成结果。


### 14.3 技术验证与故障场景

阶段0准备至少两组织、两项目、一个受邀单位、不同权限的两名分析人员，以及电子Excel、电子PDF、扫描PDF和实际计价软件导出样本。以下测试是开发及验收计划，需保留实际执行证据。

| 编号 | 操作场景 | 必须满足的结果 |
| --- | --- | --- |
| T01 | 改项目ID访问API、预览、原件、搜索、导出 | 未授权正文与聚合信息不泄露，撤权后新访问被拒 |
| T02 | SQL跨域、直接源表、复用连接与缓存 | 数据库权限拒绝越界，连接、缓存、嵌入、导出均按域隔离 |
| T03 | worker A过期，B重领完成，再恢复A提交 | 只接受有效令牌，旧执行结果不能覆盖新结果 |
| T04 | 临时文件已生成但提交前崩溃，重复投递 | 只登记一个有效结果，无重复正式发布，遗留对象可清理 |
| T05 | 并发重任务中重启、断网、短时断库 | 任务可恢复或进入可处理失败态，不静默丢失 |
| T06 | 发布后撤回，旧发布索引事件倒序到达 | 新状态不被覆盖，权威状态立即阻止原文、问答和价格条目新使用，派生索引异步收敛 |
| T07 | 生成答案过程中撤权或撤回资料 | 输出前检查阻止正文返回，引用和缓存不可绕过 |
| T08 | 旋转PDF、跨页表格、合并单元格定位 | 文件版本及页码或单元格准确，不精确时有明确提示 |
| T09 | 并发审批、重复或乱序回调、人员变更 | 单据按合法状态迁移一次，冲突阻止，异常可对账 |
| T10 | 恢复数据库与文件，清空并重建索引 | 哈希、底稿、版本及历史引用对齐，记录实际恢复指标 |
| T11 | 同码异特征、异单位、缺报价、空公式缓存 | 待核实或不可比不进基准，缺值不作零 |
| T12 | 对照任务表与成熟队列的恢复与维护代价 | 按实际人周、运维组件和故障结果冻结方案 |

T05至少覆盖三类重任务并发和十次有记录的故障注入，用于覆盖基础故障路径，不作为可靠性概率或最大容量证明。格式、权限和金额质量属于上线门槛；范围中尚缺接口或授权的能力单列条件验收，不能以人工路径替代自动化验收。

### 14.4 详细设计优先项

首先确认项目与合同数据字典、报送目录、集团资料分类和三级校审制度；随后形成六个平台菜单与页面原型、接口清单、分析规则目录及开源版本兼容矩阵。每项业务功能标明首版覆盖方式、依赖接口、样本和验收人，作为开发和验收依据。

技术验证优先打通四个样例：一份扫描合同提取并核对金额；一组控制价与送审清单量价对照；一份制度人工发布后检索引用；一个审计问题经修改和三级校审后归档。验证通过后再扩大批量处理规模。


## 十五 实施决策与版本控制

本版明确六个平台、开源复用、人工资料发布及DeepSeek接入的实现决策。开发采用项目负责人、OpenAI Dot与Codex协作方式，具体任务和排期由配套开发计划书管理。以下决策用于实施，实际部署和验证记录按版本归档。

| 讨论问题 | 优化后的决策 | 对核心目标的影响 |
| --- | --- | --- |
| 六平台是否各自部署一套系统 | 保留六个产品模块，共享核心应用和通用服务 | 平台数量与职责保持 |
| PostgreSQL还是MySQL | PostgreSQL优先POC，失败再验证备选，只维护一种 | 不改变业务与H5目标 |
| 是否先用数据库做中文正文检索 | OpenSearch在检索交付阶段默认启用 | 保留全文检索及知识服务 |
| 是否首版部署全部大数据组件 | 按功能交付场景启用，完整职责逐项验收 | 分期实现，不删除目标 |
| 是否直接部署成熟任务队列 | 低并发先用持久任务协议，按POC代价决定备选 | 保留分析任务与恢复要求 |
| 统一登录能否解决BI权限 | 分析域、数据库账号与视图构成硬边界 | 项目受限用户仍有受控查询 |
| 资料撤回只删索引是否足够 | 覆盖问答、价格条目、任务、缓存及历史快照 | 人工资料维护仍为发布前提 |
| 是否沿用4人12至16周排期 | 按工作包与真实依赖重新估算 | 六平台整体范围保持 |

本版技术依据包括业务需求、开源源码和官方技术文档。实际兼容性、识别质量、权限、任务恢复和性能由WP0及后续工作包验证，相关记录作为版本冻结与上线依据。
